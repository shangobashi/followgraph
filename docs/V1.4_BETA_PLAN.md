# FollowGraph v1.4 Beta Plan

Goal: make scan and enrichment materially faster while preserving the v1.3.7 correctness fixes: captured API enrichment, cursor-aware scan completion, saved-checkpoint recovery, and guarded unfollow review.

## Release Strategy

v1.4 beta is not a rewrite. It keeps the proven v1.3.7 architecture and removes avoidable repeated work from the hot paths.

Primary target:

- 90% or better activity resolution within the existing 90 minute acceptance gate for 7.5K accounts.
- Faster scan wall time by replacing repeated visible-list reparsing with mutation-stream extraction.
- Faster fallback enrichment by reducing repeated full-body DOM reads on profile pages.
- No regression to scan completion, checkpoint recovery, API capture, or unfollow safety.

## Implemented Scope

### 1. Incremental scan extraction

- Parse newly mounted `UserCell` nodes directly from the scroller `MutationObserver`.
- Keep cached parsing per mounted element through `WeakMap`.
- Keep a periodic full visible-list parse every 25 rounds as a safety fallback.
- Keep the initial full visible parse so already-mounted accounts are never missed.

Why: X virtualizes the Following list, so the hot path should process new mounts once instead of reparsing the same visible cards every tick.

### 2. Lower allocation store merges

- Add `UserStore.addOne`.
- Return change counts from `UserStore.add`.
- Avoid replacing an existing stored user when the merge does not improve any field.

Why: scan and API harvesting repeatedly encounter the same accounts. No-op merges should stay cheap.

### 3. Progress rendering throttle

- Limit overlay progress rendering to about 2 Hz during active scan movement.
- Still update immediately during idle/waiting ticks where user feedback matters.

Why: rendering overlay text every scroll tick is unnecessary on large scans.

### 4. Fallback profile DOM optimization

- Read profile page text once per poll.
- Reuse the same signal snapshot to detect terminal states and timeline readiness.

Why: API fast path is the primary resolver, but helper-tab fallback should avoid repeated full-body reads.

## Explicit Non-Goals For Beta

- Do not reduce cursor-aware idle thresholds. That risks ending scans too early.
- Do not remove helper-tab fallback. It is required for X API schema drift.
- Do not prewarm hidden tabs on popup open. That may increase throttling and user distrust without proven benefit.
- Do not treat following-card timestamps as sufficient. They are opportunistic only and were unreliable in large live scans.

## Verification Gates

Required before ship:

- `npm run build`
- `npx tsc --noEmit`
- `npm run test:scan-completion`
- `npm run replay:report`
- `npm run acceptance:synthetic`
- Confirm `public/downloads/followgraph-extension.zip` is regenerated from the latest `extension/` output.

Preferred live beta evidence:

- Run a real Following scan on a large account.
- Confirm total extracted count matches expected account count.
- Confirm `Resolved / total >= 90%` after API fast path and fallback.
- Confirm inactive over 30 days is populated before using unfollow review.

## Risk Controls

- The full-parse fallback prevents silent misses from MutationObserver edge cases.
- Existing saved scan checkpoints remain active throughout scanning.
- Existing cursor-aware scan completion decides when to stop; the parser optimization does not control completion.
- Existing unfollow queue still requires enriched, inactive-over-30 accounts and only runs one unfollow worker.
